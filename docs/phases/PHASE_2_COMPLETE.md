# Phase 2 complete: engine, protocol, first modules, headless CLI

Branch `phase-2-engine` · 2026-10-20 · QA report: [`PHASE_2_QA.md`](PHASE_2_QA.md)

## What shipped

### `spektr-protocol` (MODULES §2–3)
- **`Manifest`:** parsing plus a lint, which checks:
  - the name and semver
  - exec vs native fields
  - durations and rate limits
  - the extension namespace
  - secret names
- **Messages:** `HostMessage` (`hello`, `run`, `cancel`, `shutdown`) and `ModuleMessage` (`ready`, `observation`, `entity`, `attr`, `edge`, `review`, `progress`, `log`, `done`, `error`), with strict parsing.
- **JSON Schemas:** `cargo xtask schemas` generates `schemas/exec-protocol.v1.json` and `schemas/manifest.v1.json`, and CI runs `--check`.
- **Dependencies:** the crate depends only on serde, serde_json, toml and thiserror, plus schemars behind the `schema` feature.

### `spektr-engine` (MODULES §4–5)
- **Handle and events:** `EngineHandle` (`act`, `query`, `subscribe`, `wait_idle`, `status`, `modules`) and `EngineEvent`.
- **Profiles and scope:**
  - rules profiles `default` and `tracelabs`, embedded, with user profiles from `<config>/profiles/`
  - the news and aggregator blocklist
  - scope rules (`domain:`, `cidr:`, `platform:`, `regex:`, `deny`), with out-of-scope flags recomputed whenever the rules change
- **Eligibility:** a pure function covering MODULES §5 in order.
- **Planner:** runs eligibility, deduplicates against queued/running jobs, looks up the cache, checks daily budgets and writes job rows, all in one store transaction.
- **Scheduler:**
  - priority: manual, playbook and tutor before auto; then shallower depth
  - the global limit of 16, plus each module's `concurrency`
  - start pacing for exec modules
  - retries for retryable `rate_limited`/`upstream` errors: at most 2, with backoff or `retry_after`
  - cancellation
- **Ingestion:**
  - batches of up to 200 messages or 50 ms, one transaction per batch
  - validation of evidence, refs, the vocabulary and the manifest's `produces`
  - normalization, depth, implied edges, blobs, attributes, review items
  - hub refresh by degree
  - follow-up auto jobs
  - a store error rolls back the batch, emits `IngestFailed` and fails the batch's jobs
- **Correlation:** the correlator framework, plus two rules. Identity merge happens at insert, through the normalized-key upsert. The `ip` rule creates `shares_artifact` edges, skips hubs, and gives each edge a correlator observation as evidence.
- **Exec runtime:**
  - per-job mode: `hello`, `run`, read until `done`/`error`, close stdin, 2 s grace, then kill
  - serve mode: one process, `ready`, many runs routed by job id, `cancel` per job, respawn after an exit
  - limits: 32 MiB lines, 10,000 messages and 50 MiB raw per job
  - stderr goes to the log with secret values redacted
  - modules load from `<config>/modules/*/module.toml`

### `spektr-modules`
- **`net`:**
  - `Net { http, dns }` with Live / Record / Replay transports
  - HTTP over reqwest (rustls + ring), with a user agent and per-host `governor` rate limits from each manifest's `rate_limit`
  - DNS through **spektr's own stub resolver over `hickory-proto`**, the Phase 0 decision. It does UDP with EDNS0 (1232-byte payload), random query ids matched against the response's id *and* question, retries over TCP on truncation, and fails over across nameservers with two attempts each. Nameservers come from config `[dns] nameservers`, else `/etc/resolv.conf`.
- **Fixtures:** replay matches HTTP by method + normalized URL and DNS by name + record type. **A miss fails the job and is recorded as a miss.**
- **Built-ins:**
  - `dns`: A, AAAA and MX → `resolves_to`, `mail_handled_by`
  - `github`: the profile, `last_active` from the newest public event, the blog URL, the public email, and the stated location
  - `username-sweep`: **307 sites** in `data/sites.json`, overridable by id from `<config>/sites.json`
- **Fictional fixtures:** GitHub and DNS fixtures are hand-written. The sweep fixture is generated by `fixture_lines()`, and a test keeps the committed copy current.

### `spektr` (binary)
- **Commands:** `new`, `run`, `query` (`--type`, `--match` fuzzy, `--neighbors`, `--predicate`, `--path`, `--findings`, `--json`), `verify` (`--json`, exit 3), `export --format json` (`--with-blobs`, `-o`) and `doctor` (`--json`).
- **Environment:**
  - XDG paths (§5): never `dirs::config_dir()`
  - `config.toml`, with secrets from `[secrets]` overridden by `SPEKTR_SECRET_*`
  - a daily rolling log in the state dir, with secrets redacted
  - test variables gated by `SPEKTR_TEST_MODE=1`, documented under "Testing" in `--help`
  - exit codes 0 / 1 / 2 / 3

### QA groundwork (QA.md)
- **PTY harness:** `crates/spektr/tests/support/term.rs`, built on portable-pty + vt100. It reads the screen with colours, has a key DSL and SGR mouse input, handles resize and exit codes, and saves `.txt` / `.ansi` / `.html` frames.
- **E2E tests:** `e2e_headless`, `e2e_verify` and `e2e_pty_smoke`.
- **Commands:**
  - `cargo xtask qa` runs `qa/scenarios/*.toml`
  - `cargo xtask qa --live` runs approved targets only
  - `cargo xtask qa-shots` renders frames and artboards with headless Chrome
  - `cargo xtask record <module> <input>` takes approved targets only and writes to `target/recordings/`
- **Example config:** `qa/live-targets.toml.example`.
- **First live smoke run:** done (in PHASE_2_QA).

## Deviations from the spec, and why

1. **DNS uses `hickory-proto` plus spektr's own stub resolver** (Jay's decision in Phase 0, recorded in DEPENDENCIES.md). MODULES §6 now says `dns` uses the system nameservers through this resolver, and config gains `[dns] nameservers`.
2. **Protocol additions, all optional.** The schema is now fixed from the end of Phase 2. These are documented in MODULES §3.3:
   - `observation.summary`: a small JSON object, stored with the observation
   - `entity.key`: a certificate's identity when its `value` is a display label
   - retries require `retryable: true` *and* a `rate_limited`/`upstream` code; the spec's example implied this, and the engine originally ignored the module's flag
   - job ids on the wire are `j_<uuid>`
3. **`spektr-protocol` doesn't depend on `spektr-model`.** It mirrors `AttrValue` with string times and dates, and the engine converts. That keeps third-party Rust modules on serde alone.
4. **How `produces` gates output.** A module may emit an edge only if `produces` names its predicate. It may emit an entity only if the entity's type appears in a `produces` pair, or is the input's own type. Modules may never assert `shares_artifact` (correlators only) or `depicts` (analysts only).
5. **How blocked differs from ineligible, by trigger.**
   - Rules-profile blocks are always recorded as `blocked`, whatever the trigger (J3).
   - A disabled module, a missing secret or an exhausted budget is recorded as `blocked` for manual, playbook and tutor triggers. For auto triggers it is silently ineligible, so an unconfigured keyed module doesn't write a blocked row for every new entity.
   - Scope and hubs block playbook jobs (PLAYBOOKS §2) and filter auto jobs. Manual and tutor runs, including `:expand`, go ahead.
6. **The sweep site list's detection rules are unverified live** (see Known issues).
   - **Methods:** `status`, `absent_text`, `present_text`, `redirect`, and a fifth, `login_wall`, for profiles that can't be checked without logging in. Those are always "unsure" (MODULES §6 lists the login wall as an unsure condition).
   - **Skipped sites:** sites whose platform rules can't take the handle (e.g. a dot on GitHub) are skipped without a request. The summary records them as `skipped`; the progress note counts them under `none`, giving `307 sites · 7 found · 5 unsure · 295 none`.
   - **Size:** 307 sites, meeting MODULES §6's "~300" with 168 new platforms added to `platforms.rs`.
7. **QA in Phase 2 is CLI-only.** There's no TUI yet, so no frame has an artboard to match. The artboards rendered for Phase 3 need preprocessing because `docs/design/` references a `support.js` that isn't in the repo (PHASE_2_QA, bug 4).
8. **Exec modules load without install pinning.** Tree-hash pinning and `spektr module install` are Phase 5. Until then, any `module.toml` under `<config>/modules/` is loaded, and the doctor lists them.
9. **A job that wrote no observation isn't cached.** For example, `github` on a handle GitHub can't have makes no request. The cache is keyed on observations (MODULES §5).
10. **`spektr` with no arguments prints help.** The launcher is Phase 3. `export --format md|tracelabs` exits 1 with "arrives with findings (Phase 5)".
11. **Seeded ids are salted with the case's audit length on open.** This keeps `SPEKTR_SEED` deterministic across several invocations on one case; without it, ids collided (bug found by `e2e_headless`).
12. **The binary uses `nucleo-matcher` for `query --match` and `which` for doctor checks.** Both are already workspace dependencies.

## Known issues

- **The 307 sweep sites haven't been checked live.** `qa/live-targets.toml` lists no usernames, so `username-sweep` (and `github`) haven't run against the real sites. Detection rules come from my knowledge of those sites and may have drifted; a wrong rule produces false positives or "unsure" items. **To verify:** add a username you own to `qa/live-targets.toml` and run `cargo xtask qa --live`, or approve using a random, unclaimed handle for false-positive checks.
- **Serve mode can't attribute a non-JSON line to a job.** That job waits for its timeout unless the process exits first. Per-job mode fails the job immediately.
- **Exec modules are rate-limited by job-start pacing only.** The engine can't see their traffic (MODULES §5 allows this).
- **The doctor's resolver line shows the machine's LAN resolver.** That's real system state, not a bug.
- **The QA harness renders "default colour" cells with constants copied from the `bg`/`fg` tokens.** Phase 3 will source them from `theme.rs`.

## How Jay can test it

1. `git checkout main && git pull`, then `cargo nextest run --workspace`. Expect `133 tests run: 133 passed, 1 skipped`.
2. Run the headless flow against fixtures:
   ```sh
   export SPEKTR_TEST_MODE=1 SPEKTR_TRANSPORT=replay:$PWD/crates/spektr-modules/fixtures
   spektr new demo --profile tracelabs && spektr run demo.spektr --seed username:jmarlow.wav
   spektr query demo.spektr --neighbors username:jmarlow.wav
   spektr export demo.spektr --format json | head -40
   spektr verify demo.spektr
   ```
3. Run it live on something you own, with no test variables set: `spektr new live && spektr run live.spektr --seed domain:<your domain>`. The `dns` module resolves it through spektr's resolver.
4. `cargo xtask qa && cargo xtask qa-shots`, then open `qa/out/*/*.png` and `qa/out/artboards/*.png`.
5. Optional: add usernames you own to `qa/live-targets.toml` (copy `qa/live-targets.toml.example`) and run `cargo xtask qa --live`. That's the only way to verify the sweep's site rules.
